# PassGuard — управление секретами

Курсовая работа по дисциплине «Управление информационной безопасностью».
Тема 7: «Безопасное хранение и замена паролей и ключей».

**Этап 1:** локальный стенд Vault + PostgreSQL + FastAPI, получение пароля
из защищённого хранилища, его фактическая замена в PostgreSQL и проверка
того, что старый пароль перестал приниматься.

**Этап 2:** отдельный управляющий API с входом, серверными сессиями,
ролями пользователей, аудитом и заменой пароля через авторизованный запрос.

**Этап 3:** проверка ZIP с исходниками через Gitleaks в отдельном контейнере,
очищенные отчёты, права запуска и аудит проверок.

**Этап 4:** панель React с входом, обзором стенда, ротацией, проверками,
отчётами, журналом и управлением доступом.

## Что реализовано

- Vault в обычном серверном режиме с постоянным Raft-хранилищем.
- TLS с проверкой локального центра сертификации для Vault и PostgreSQL.
- Автоматическая первоначальная настройка, без паролей в исходном коде.
- Отдельные AppRole-идентичности для приложения и оператора ротации.
- Приложение читает только свой пароль; оператор может заменить пароль,
  но не может прочитать его.
- Учебная учётная запись БД читает только таблицу `demo.documents`.
- Реальная ротация через Database Secrets Engine Vault.
- Аудит обращений к Vault; начальный root-токен отзывается после настройки.
- Повторное получение секрета при его изменении между чтением и подключением.
- Автоматическое испытание с отчётом, в котором нет значений секретов.
- Модульные проверки и workflow GitHub Actions для проверки живого стенда.

Управляющий API поддерживает роли `admin`, `operator`, `auditor`, защиту
изменяющих запросов CSRF-токеном, отзыв сессий, ограничение попыток входа
и идемпотентные операции ротации. Его пароль БД также получает из Vault.
Сканер не получает доступ к Vault и БД. Панель React работает с настоящим
управляющим API; ИИ-помощник добавляется следующим этапом.

## Панель: обновление после третьего этапа

```powershell
git pull --ff-only
docker compose --profile ops build
docker compose up -d --wait demo control
docker compose run --rm tools python -m scripts.verify_panel
```

Открой <http://127.0.0.1:8000/>. Вход — существующей учётной записью;
первоначальный логин сохранён в `.local/operator/control-admin.json`.
При уже изменённом пароле используй актуальное значение. Node.js на компьютер
устанавливать не нужно: панель собирается внутри Docker.

Новых миграций нет. Пользователи, секреты и отчёты сохраняются. Если Vault
запечатан после перезапуска, сначала выполни
`docker compose run --rm tools python -m scripts.unseal`.

Ожидается `status: passed`; результат — `reports/panel.json`. Документация API
остаётся на <http://127.0.0.1:8000/docs>.
[Экраны, права, ротация и разработка](docs/panel.md).

## Проверка исходников: обновление после второго этапа

```powershell
git pull --ff-only
docker compose --profile ops build
docker compose run --rm tools python -m scripts.setup_scanner
docker compose up -d --wait demo control
docker compose run --rm tools python -m scripts.verify_scanner
```

Сканер запустится автоматически вместе с `control`. Ожидается `status: passed`;
результат испытаний сохраняется в `reports/scanner.json`. Пользователи и секреты
существующего стенда сохраняются. При запечатанном Vault сначала выполни
`docker compose run --rm tools python -m scripts.unseal`.

В <http://127.0.0.1:8000/docs> доступны `POST /api/control/scans` для ZIP
и `GET /api/control/scans` для списка результатов. Запуск разрешён ролям
`admin` и `operator`, чтение также разрешено `auditor`. Находки содержат
путь, строку и правило без значений из содержимого файлов. Это проверка снимка
исходников UTF-8; история Git не анализируется, пропуски бинарных файлов
отмечаются отдельно. [Инструкция и ограничения](docs/source-scanning.md).

## Быстрый запуск на Windows

Нужен запущенный **Docker Desktop** в режиме Linux containers с Docker Compose v2.
Python и PostgreSQL на компьютер устанавливать не требуется.
Клонируй репозиторий и открой его папку в VS Code:

```powershell
git clone https://github.com/Ghost2772/passguard.git
cd passguard
code .
```

Также можно извлечь архив проекта. Выполняй команды в PowerShell
из папки, содержащей `compose.yaml`.

```powershell
docker version
docker compose version
```

Собери служебный образ и демонстрационное приложение:

```powershell
docker compose --profile ops build
```

Создай локальные сертификаты и начальный пароль БД:

```powershell
docker compose run --rm --no-deps tools python -m scripts.prepare
```

Запусти хранилище и БД, затем выполни первоначальную настройку:

```powershell
docker compose up -d postgres vault
docker compose run --rm tools python -m scripts.bootstrap
```

Дождись сообщения об успешной настройке и запусти приложение:

```powershell
docker compose up -d --wait demo
docker compose ps
```

Открой:

- Документацию API: <http://localhost:8001/docs>
- Учебные документы: <http://localhost:8001/api/documents>
- Проверку готовности: <http://localhost:8001/ready>

Ожидаемый ответ с документами:

```json
{
  "items": [
    {"id": 1, "title": "Политика управления секретами"},
    {"id": 2, "title": "Порядок замены паролей"}
  ]
}
```

## Испытание для курсовой

```powershell
docker compose run --rm tools python -m scripts.verify_rotation
```

Проверка выполняет настоящие обращения к Vault, PostgreSQL и приложению:

1. Подтверждает работу приложения до замены.
2. Получает старый пароль в память испытательного процесса.
3. Проверяет, что приложению запрещена ротация, а оператору запрещено чтение пароля.
4. Проверяет запрет записи на уровне прав PostgreSQL.
5. Вызывает ротацию статической роли в Vault, изменяющую пароль пользователя БД.
6. Подтверждает изменение пароля.
7. Создаёт **новое** соединение со старым паролем и ожидает именно ошибку авторизации.
8. Создаёт новое соединение с актуальным паролем и проверяет успех.
9. Выполняет пять запросов к приложению без его перезапуска.

При успехе выводится `"status": "passed"`, а результат сохраняется
в `reports/rotation.json`. Отчёт содержит результаты проверок и время,
без паролей, токенов и строк исходного кода. Если повторное испытание
завершилось ошибкой, отчёт заменяется результатом `failed`.

Смена пароля PostgreSQL сама по себе не закрывает уже установленные соединения.
Поэтому испытание проверяет именно новые подключения. Для случая активной
компрометации прекращение прежних сессий рассматривается отдельно.

## Управляющий API: обновление существующего стенда

После успешной проверки первого этапа выполни из той же папки проекта:

```powershell
git pull --ff-only
docker compose --profile ops build
docker compose up -d --no-deps --force-recreate vault
docker compose run --rm tools python -m scripts.setup_control
docker compose up -d --wait demo control
docker compose run --rm tools python -m scripts.verify_control
```

Контейнер Vault пересоздаётся для загрузки обновлённого HCL-файла. Данные
его тома сохраняются. `setup_control` разблокирует тот же Vault, добавляет
отдельную управляющую БД и её политику доступа; учебные документы сохраняются.
Повторный `setup_control` сохраняет пользователей и их пароли.

Адреса управляющего API:

- <http://127.0.0.1:8000/docs> — документация и ручные запросы;
- <http://127.0.0.1:8000/ready> — готовность управляющей БД и Vault.

Начальный логин и случайный пароль администратора создаются локально в
`.local/operator/control-admin.json`. Открой этот файл на своём компьютере,
например через VS Code. Это операторский файл; он не попадает в Git, образы,
контейнер управляющего API и отчёты испытаний. После смены пароля аккаунта
первоначальный пароль из файла перестаёт действовать и файл не обновляется.

В Swagger сначала выполни `POST /api/control/auth/login`. Браузер сохранит
HttpOnly-cookie, а ответ вернёт `user` и `csrf_token`. Для POST и PATCH после
входа указывай этот CSRF-токен в поле заголовка `X-CSRF-Token`.
`GET /api/control/auth/me` возвращает текущего пользователя и его CSRF-токен.

| Действие | admin | operator | auditor |
| --- | --- | --- | --- |
| Просмотреть метаданные учебного секрета | Да | Да | Да |
| Проверить доступность demo | Да | Да | Нет |
| Заменить пароль demo-db | Да | Нет | Нет |
| Просмотреть журнал действий | Да | Нет | Да |
| Создавать пользователей, менять роли и активность | Да | Нет | Нет |
| Сменить собственный пароль и выйти | Да | Да | Да |

Длина нового пароля — от 15 до 128 символов; пароли хешируются Argon2id.
Сессия действует 8 часов. Выход, смена пароля и блокировка отзывают сессии
на сервере. Изменение роли также завершает сессии соответствующего пользователя.
Сервис защищает последнего активного администратора от отключения и понижения.
После 10 неудачных входов с одного IP действует ограничение на 15 минут.

Для `POST /api/control/secrets/demo-db/rotate` передай новый UUID в
`idempotency_key` и причину `manual_test`, `scheduled` или `suspected_exposure`.
Повтор с тем же ключом возвращает сохранённую операцию и не меняет пароль снова.
Статусы `in_progress` и `unknown` требуют проверки результата оператором;
повторное выполнение таких операций автоматически не производится.

Проверка `scripts.verify_control` создаёт временные учётные записи с префиксом
`verify_` и затем деактивирует их. Она проверяет реальную замену пароля через API,
роли, CSRF, завершение и истечение сессий, аудит и идемпотентность.
Отчёт без значений секретов сохраняется в `reports/control.json`.
Флаг `--check-last-admin` используется только в одноразовом стенде CI.

Подробнее об архитектуре обновления: [docs/control-api.md](docs/control-api.md).

## Остановка и повторный запуск

```powershell
docker compose down
```

Данные PostgreSQL, секреты и журнал Vault остаются в именованных томах Docker.
При перезапуске обычный Vault находится в запечатанном состоянии; разблокируй его:

```powershell
docker compose up -d postgres vault
docker compose run --rm tools python -m scripts.unseal
docker compose up -d --wait demo
```

Если управляющий API уже настроен, последнюю команду замени на
`docker compose up -d --wait demo control`.

Повторный `scripts.prepare` сохраняет существующие материалы. Повторный
`scripts.bootstrap` после завершённой настройки только разблокирует Vault
и не пересоздаёт секреты. Не удаляй `.local/`: в ней находятся данные доступа
и ключ разблокировки. Не используй `docker compose down --volumes`
для обычной остановки: эта команда удаляет данные стенда.

## Диагностика

```powershell
docker compose ps
docker compose logs --tail 60 postgres vault demo
```

- Docker не отвечает: запусти Docker Desktop и дождись готовности.
- Есть сообщение об отсутствии secret-файла: выполни `scripts.prepare`.
- Vault запечатан: выполни `scripts.unseal`.
- Порт 8001 занят: измени только левую часть привязки порта для `demo`
  в `compose.yaml`, например `127.0.0.1:8011:8001`.
- `demo` имеет статус healthy, но API недоступен с компьютера:
  проверь `docker compose port demo 8001` и попробуй
  `http://127.0.0.1:8001/ready`. Приложение должно быть подключено к обеим
  сетям `web` и `backend`; сеть `web` нужна для публикации порта.
- Нельзя скачать образы: проверь доступ Docker Desktop к Docker Hub.
- После восстановления только части файлов не запускай повторную генерацию
  поверх работающего стенда: ключи и данные должны принадлежать одной установке.

## Проверки разработки

Для локального запуска тестов нужен Python 3.12:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest
```

Модульные проверки используют тестовые ответы Vault и имитацию соединений БД.
Они проверяют обработку ошибок, повторную авторизацию, обновление пароля при
подключении, ограничение повторов и отсутствие чувствительных значений в ответах.
Они не заменяют испытание настоящих Vault и PostgreSQL.

GitHub Actions запускает модульные проверки и отдельное интеграционное задание:
сборку Docker, первоначальную настройку, HTTP-запрос к опубликованному порту
с хоста Docker, ротацию и повторную проверку после перезапуска Vault.
Если workflow ещё не запускался, интеграционная проверка
не считается пройденной.

## Структура

| Путь | Назначение |
| --- | --- |
| `src/passguard/` | FastAPI, клиент Vault, подключение к PostgreSQL |
| `src/passguard/control/` | Авторизация, сессии, роли, аудит, управляющий API |
| `scripts/` | Подготовка, первоначальная настройка, разблокировка, испытание |
| `infra/vault/` | Настройка Vault и политики доступа |
| `infra/postgres/` | TLS-запуск PostgreSQL и правила аутентификации |
| `tests/` | Модульные проверки |
| `.github/workflows/ci.yml` | Проверки в GitHub Actions |
| `docs/architecture.md` | Архитектура, границы доверия и ограничения |
| `docs/roadmap.md` | Последующие этапы курсовой |

В `.local/` генерируются ключи и идентификаторы конкретной установки.
Эта папка исключена из Git и Docker build context. Docker Compose secrets
в локальном режиме используют файлы хоста: они не являются самостоятельным
зашифрованным хранилищем и требуют защиты диска и доступа к компьютеру.
