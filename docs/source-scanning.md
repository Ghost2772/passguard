# Проверка исходников — этап 3

Сканирование выполняет Gitleaks 8.30.1 с его стандартными правилами и учебным
правилом поиска строковых паролей. Проверяется снимок текстовых файлов UTF-8
из ZIP. История Git, вложенные архивы, бинарные файлы и другие кодировки в эту
версию проверки не входят. Бинарные файлы и неподдерживаемые кодировки явно
перечисляются в `skipped_files`; отсутствие находок не доказывает отсутствие
секретов. Совпадения имеют статус `suspected` и требуют проверки человеком.

## Обновление существующего стенда

После успешного второго этапа, в той же папке проекта:

```powershell
git pull --ff-only
docker compose --profile ops build
docker compose run --rm tools python -m scripts.setup_scanner
docker compose up -d --wait demo control
docker compose run --rm tools python -m scripts.verify_scanner
```

`setup_scanner` добавляет таблицу и права через локальный служебный контейнер.
Он не сбрасывает пользователей, не меняет пароли и не требует root-токена
Vault. Повторное выполнение безопасно. На новом стенде сначала пройди настройку
первого и второго этапов из README, затем выполни эти команды.

Если Vault был перезапущен и запечатан, перед запуском приложений разблокируй
его командой `docker compose run --rm tools python -m scripts.unseal`.

При успехе испытаний `reports/scanner.json` содержит `status: passed`,
результаты проверок и количество учебных находок. Значения учебных секретов
случайно генерируются в памяти проверки; работающих внешних ключей в ней нет.
Созданные испытанием пользователи деактивируются после завершения.

## Проверка своего проекта

Для Git-проекта удобнее создать ZIP из отслеживаемых файлов. Команда не включает
неотслеживаемые файлы и локальные изменения, которые ещё не закоммичены:

```powershell
git archive --format=zip --output=source-snapshot.zip HEAD
```

Для проверки незакоммиченных изменений создай ZIP выбранных исходных файлов
обычным архиватором. Не добавляй `.local`, `.git`, `.venv`, `node_modules`
и другие служебные каталоги. Не архивируй всю папку рабочего стенда.

Открой <http://127.0.0.1:8000/docs>. Выполни `POST /api/control/auth/login`,
затем `POST /api/control/scans`: выбери ZIP и укажи `X-CSRF-Token` из ответа
на вход. Передаётся тело `application/zip`, а не multipart-форма.

| Запрос | admin | operator | auditor |
| --- | --- | --- | --- |
| `POST /api/control/scans` — начать проверку | Да | Да | Нет |
| `GET /api/control/scans` — список результатов | Да | Да | Да |
| `GET /api/control/scans/{id}` — сохранённый отчёт | Да | Да | Да |

Отчёт содержит идентификатор проверки, время, автора, версию сканера и результат:

```json
{
  "engine": "gitleaks",
  "engine_version": "8.30.1",
  "scope": "source_snapshot",
  "files_scanned": 3,
  "bytes_scanned": 1000,
  "findings": [{
    "id": "F0001",
    "file_id": "file_0001",
    "path": "src/config.py",
    "line": 4,
    "end_line": 4,
    "rule_id": "passguard-hardcoded-password",
    "kind": "password",
    "severity": "high",
    "status": "suspected"
  }],
  "skipped_files": []
}
```

Названия файлов считаются пользовательскими данными. Будущий ИИ-помощник
должен получать только `file_id`, номера строк, тип и идентификатор правила;
пути, содержимое файлов и исходные данные детектора ему не передаются.
Сканирование не запускает автоматическую ротацию.

## Границы доступа и обработка файлов

Публичен только управляющий API на loopback-порту. Сканер не публикует порт
на хосте и подключён к отдельной внутренней сети `scanning`. Он не подключён
к `backend`, не получает идентичность Vault, пароль БД, операторские файлы
или Docker socket. Внутренний HTTP-интерфейс сканера доступен управляющему
контейнеру; авторизацию, CSRF и аудит обеспечивает управляющий API.
Стенд рассчитан на доверенный Docker-хост и локальную учебную работу.

Сканер работает без root, с файловой системой только для чтения, отключёнными
Linux capabilities и ограничениями памяти, процессора и числа процессов.
Временные данные размещаются в `tmpfs` с `noexec`, в закрытом каталоге;
файлы проекта не исполняются. Каталог удаляется при штатном завершении
или обработанной ошибке. После аварийного завершения процесса оставшиеся
временные данные исчезают при пересоздании контейнера.

| Ограничение | Значение |
| --- | --- |
| Размер тела ZIP | 5 МиБ, включая потоковые загрузки без Content-Length |
| Файлов | 1000 |
| Размер распакованного файла | 1 МиБ |
| Общий распакованный размер | 20 МиБ |
| Находок в одном результате | 1000; превышение возвращает ошибку |
| Время загрузки | 20 секунд |
| Время Gitleaks | 20 секунд, принудительное завершение через 25 секунд |
| Одновременных проверок | 1; дополнительный запуск возвращает 429 |

Пути с `..`, абсолютные пути, управляющие символы, обратные слеши,
повторяющиеся имена, ссылки, шифрование и специальные файлы отклоняются.
Размеры проверяются до и во время чтения; `extractall` не используется.
Для детектора создаются плоские сгенерированные имена, сохраняется безопасное
расширение. Исходный путь возвращается по отдельному соответствию в памяти.
Поэтому правила, зависящие от точного исходного имени/каталога файла, могут
не сработать; основная проверка относится к содержимому файлов.

Конфигурация и шаблон отчёта задаются приложением. Загруженные `.gitleaks.toml`,
`.gitleaksignore` и комментарии `gitleaks:allow` не отключают проверку.
Шаблон детектора выводит только сгенерированное имя, правило и номера строк.
Дополнительно используется полное редактирование Gitleaks; stdout/stderr
детектора не публикуются. Поля `Secret`, `Match`, фрагменты строк, комментарии
и сведения об авторах коммитов не включаются в отчёт. Данные повторно проходят
строгую схему перед записью в БД. В журнале хранятся действие, количество
находок и фиксированный код ошибки, без исходников и значений секретов.

Для находок задан отдельный код завершения 10: код 1, таймаут или частичная
проверка не считаются чистым результатом. Отчёты неизменяемы для сервисной
учётной записи БД. Это ограничение не защищает от администратора самого
PostgreSQL; срок хранения отчётов определяет оператор стенда.
