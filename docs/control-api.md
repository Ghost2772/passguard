# Управляющий API — второй этап

## Разделение компонентов

`demo` остаётся потребителем учебной БД на порту 8001. Управляющий сервис
`control` работает на порту 8000 от UID 10002. Оба порта привязаны к
`127.0.0.1`; сервисы имеют сеть `web` для HTTP-публикации и сеть `backend`
для обращения к Vault и PostgreSQL.

Пользователи, сессии и аудит находятся в отдельной БД `passguard_control`.
Учётная запись `control_api` получает права только на управляющую схему.
Vault хранит и меняет её пароль через отдельное подключение `control` и
статическую роль `control-db`. Приложение получает текущий пароль при каждом
новом подключении и повторяет только установление соединения при ошибке
авторизации. Операции SQL автоматически не воспроизводятся.

## Политика Vault

| Путь | Возможности control |
| --- | --- |
| `database/static-creds/control-db` | Чтение собственного пароля БД |
| `database/static-roles/demo-db` | Чтение метаданных роли |
| `database/rotate-role/demo-db` | Запуск ротации учебного пароля |

У управляющего API нет права читать `database/static-creds/demo-db`.
Значение учебного пароля остаётся доступным только потребителю `demo` и
локальному испытательному процессу с его идентичностью.

## Обновление уже работающего первого этапа

Начальный root-токен первого этапа отозван. Локальная команда `setup_control`
использует хранящийся у оператора Shamir-ключ, чтобы авторизовать новую выдачу
root-токена через штатный API Vault. На Vault 2.2 включена совместимость
`enable_unauthenticated_access=["generate-root"]`: запуск процедуры доступен
в сети backend, а её завершение требует сохранённого Shamir-ключа.

Токен используется только в памяти команды настройки и отзывается в `finally`,
в том числе при обычной ошибке настройки. Завершение процесса или хоста без
исполнения `finally` не покрывается этой гарантией. Отдельный многоключевой
порядок администрирования для производственной среды здесь не реализован.
HTTP-сервис не получает root-токен, Shamir-ключ или пароль postgres.

Команда добавляет отдельные роли и БД, не пересоздавая тома первого этапа.
Учебная упрощённая модель с одним Shamir-ключом и доверием администратору
компьютера сохраняется. Путь `sys/raw` и режим recovery не используются.

## Пароли и сессии

Пароли пользователей хешируются Argon2id с параметрами рекомендованного
хешера pwdlib. Начальный пароль администратора генерируется отдельно для
установки и сохраняется в операторской папке до первого входа. Пароль не
попадает в исходники. API возвращает только разрешённые поля пользователя.

Идентификатор сессии имеет 256 бит случайности, в БД сохраняется его SHA-256.
Это высокоэнтропийный случайный токен, а не пароль пользователя. Браузер
получает его только в HttpOnly-cookie с `SameSite=Strict`, путём `/api/control`
и сроком 8 часов. Для локального HTTP `Secure=false`; при HTTPS необходимо
включить `COOKIE_SECURE=true`. Пароли и сессии не передаются в URL.

Каждый защищённый запрос проверяет существование сессии, её срок, состояние
пользователя и актуальную роль. Выход удаляет сессию. Смена пароля, блокировка
и изменение роли удаляют сессии пользователя. Глобальная транзакционная
блокировка защищает проверку последнего администратора при параллельных запросах.

CSRF-токен связан с серверной сессией и возвращается после входа и в `auth/me`.
Изменяющие запросы требуют `X-CSRF-Token`. Отдельно проверяется Origin/Referer
браузерного запроса. По умолчанию разрешены только локальные адреса API.
CORS не включает произвольные источники; будущий React использует прокси
или явный список разрешённых источников.

## Аудит и операции

В журнал входят входы, отказы, создание пользователей, изменения прав,
выходы, замены пользовательских паролей, проверки и ротации секретов.
Пароли, их хеши, session ID и CSRF-токены не записываются в журнал.
У runtime-роли БД есть только SELECT и INSERT для таблицы аудита.
Администратор PostgreSQL и администратор хоста остаются доверенными:
защита журнала от них и независимое хранилище аудита добавляются отдельно.

Сначала ротация фиксируется как `in_progress`, затем вызывается Vault,
затем сохраняются результат и событие аудита. UUID идемпотентности защищает
от повторного запуска при повторе запроса. При неясном результате вызова
Vault операция получает `unknown`. При аварийном завершении процесса
операция может остаться `in_progress`; повтор с тем же ключом возвращает
её состояние. Распределённая атомарность между Vault и PostgreSQL не заявляется.

Схема БД создаётся SQL-файлом `infra/postgres/control-schema.sql`.
Второй этап добавляет первую версию управляющей схемы; дальнейшие изменения
схемы потребуют отдельных миграций.
