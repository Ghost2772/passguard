# Применение PassGuard для будущего интернет-магазина

PassGuard можно использовать как основу управления служебными секретами
магазина. Текущая конфигурация обслуживает учебный секрет `demo-db` и
учётную запись `demo_reader`. Подключение реального магазина требует
отдельной настройки доступа и изменения его бэкенда; это план расширения,
а не уже выполненная интеграция с магазином.

| Данные | Предполагаемое место и способ хранения |
| --- | --- |
| Пароль подключения бэкенда магазина к БД | Отдельная роль Database Secrets Engine Vault, отдельная служебная учётная запись магазина |
| Ключи платёжного сервиса, доставки, почтовые секреты | Отдельные пути Vault, например KV v2; поддержку записи, чтения по политике и интерфейс потребуется добавить |
| Пароли покупателей и администраторов магазина для входа на сайт | Хеши Argon2id с солью в БД самого магазина; восстановление исходных значений для входа не требуется |
| Имя, почта, адрес и заказы покупателя | Прикладные данные в БД магазина, с собственными правилами доступа и защиты |

Различие связано с задачей: служебный пароль нужен бэкенду для предъявления
другому сервису, а пароль покупателя при входе проверяется по хешу.
Для пользовательских паролей OWASP рекомендует адаптивные алгоритмы
хеширования, включая Argon2id. Хранилище секретов не заменяет регистрацию,
вход, сессии и разграничение доступа в самом магазине.

План подключения служебного пароля БД:

1. Создать для магазина собственную служебную учётную запись с необходимыми
   правами на его таблицы. Учебная `demo_reader` предназначена только для
   чтения документов и не подходит для создания заказов и изменения корзины.
2. Настроить отдельную роль Vault и отдельную идентичность бэкенда магазина.
   Разрешить ей читать только собственные данные подключения. Управление
   ротацией выделить отдельно от обычной работы приложения.
3. Научить бэкенд получать актуальные данные подключения по TLS.
   Браузер покупателя не получает доступ к Vault или служебному паролю.
4. Адаптировать соединения с БД к ротации. Если магазин использует пул,
   потребуется обновление/пересоздание соединений и обработка отказов
   авторизации. Учебный приём «новое соединение на каждый запрос» нельзя
   автоматически считать подходящим для нагрузки магазина. Повтор записи
   заказа после сетевой ошибки не должен приводить к дублированию заказа.
5. Проверить интеграцию на тестовом окружении магазина: вход, каталог,
   создание заказа до и после ротации, отказ старому паролю в новом соединении.
   Рабочие данные и платёжные ключи в учебное испытание не включать.

Для API-ключей хранение и отзыв — отдельные операции. Изменение значения
в Vault само по себе не отключает прежний ключ у платёжного, почтового
или другого провайдера. Ротация потребует процедуры или адаптера именно
этого провайдера и согласованного обновления потребителей.

До использования реальных секретов потребуется подготовка серверного
размещения. В текущем стенде панель работает по локальному HTTP,
`COOKIE_SECURE=false`, используется один узел Vault и учебный ключ
разблокировки с порогом 1, сохранённый локально у оператора.
Эти свойства удобны для воспроизводимой курсовой и не означают, что
конфигурация уже готова защищать работающий магазин в интернете.

Для реального размещения нужно отдельно настроить HTTPS и secure-cookie,
ограничить доступ к управляющей панели и внутренним сервисам, защитить
ключи разблокировки и начальные идентичности, организовать резервные копии
Vault с проверкой восстановления, мониторинг и порядок обновлений.
Также нужен план доступности: потеря доступа к хранилищу влияет на создание
новых подключений приложения. Размещение Vault на одном узле с магазином
сохраняет общую границу риска при компрометации администратора хоста.

Для магазина можно повторно использовать существующие механизм выдачи
секрета, TLS, политики доступа, аудит и проверку исходников. Конфигурацию
конкретного магазина, его подключение и эксплуатационные меры нужно
подготовить и испытать отдельно.
